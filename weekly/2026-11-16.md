## 本周最值得深读的技术变化

### 1. Tool RL 不仅要训练“调对工具”，还要训练“此刻应不应该调用”

[StateAlign](https://arxiv.org/abs/2611.16304) 用五种任务状态构造对比样本：同样的用户目标，在“信息缺失、工具不可用、执行条件满足”等不同状态下，正确动作可能是追问、检索、调用、拒绝或继续。它在 outcome reward 以外增加状态对比的 token-level 优化目标。论文的 Qwen3-8B 多轮准确率和工具幻觉指标同步改善，但仍需独立验证中文工具集和线上流量。

**可迁移到 SearchAgent**：每个轨迹抽出 `[query, available_tools, known_evidence, current_subgoal, progress]` 状态，在状态条件变化时检查动作是否从 tool_call 转为 ask / retrieve / stop；避免把“多调用工具”错误地当作更主动的 Agent 能力。

### 2. 多 Agent 的 Reward 分配粒度，可以落到“子 Agent 报告”

[LEAD-RL](https://arxiv.org/abs/2611.17041) 使用训练期 Rubric 对每个 subagent report 判断 helpful / neutral / harmful。它并非给模型另外加一个“速度奖励”；仍用 final answer correctness 作为团队级目标，但对各子 Agent 继承 team advantage 的方式做门控，避免有用的报告因为主 Agent 汇总失败而被整体惩罚，也避免坏报告因整体幸运成功被奖励。

对 DeepResearch、并行 Web Search、商品搜索，多线程子任务的召回/证据质量应分别审计。值得比较：shared team reward、per-report rubric gating、单 Agent 对照三组；报告 Answer correctness、引用证据有效率、critical-path cost、总 token 以及 wall-clock RT。注意 critical-path cost 不等于真实线上提速。

### 3. 检索优化开始关注“索引内存”和“推理上下文”两种不同预算

[Token Pooling-Aware Training](https://huggingface.co/blog/token-pooling) 面向 ColBERT 类多向量检索：用 full-vector 与 pooled-vector 两种训练目标约束表示，压缩前后都要能检索；一个可复现示例在 NanoBEIR@13 的 pool_factor=4 设置下从 49.03 提升至 51.23 nDCG@10，存储的文档 token 向量数减少约 74.8%。这是**索引压缩**，不是 LLM context 压缩。

[OpticalRAG](https://arxiv.org/abs/2611.13675) 则把检索证据通过视觉表示和 query-conditioned distillation 压到 16 个前缀 token，再交给语言模型；这是**上下文压缩**。对多模态文档检索有启发，但必须加算图像渲染、视觉 encoder、离线缓存、首次请求延迟与引用定位开销。两种方法优化的预算层次不同，不能把收益直接相加。

### 4. Jev / 非生成式 Judge 开始出现更统一的工具接口

Hugging Face 于 [11 月 10 日发布 Decision Models](https://huggingface.co/blog/decision)，将这类模型描述为：输入 state、问题和限定答案，直接返回决策及其概率分布，而非逐 token 生成自然语言。文章给出 Transformers `pipeline("decision")`、llama.cpp serving 等实践，并明确了 Jev 与 decision model 的术语关系。

这非常适合 Rubric 的离散化判决：比如 0/1/2/3 档、多维标签、主诉求是否满足、事实错误类型。**但概率输出不自动等于校准后的可信度**；应评估人工一致率、严重错判率、ECE/Brier、跨语言等价改写、冷/热缓存、p50/p95 RT，以及每千例成本，而不仅是 benchmark accuracy。

### 5. Workflow 与 Skill 是独立于底座模型的能力

[WorkflowArena](https://arxiv.org/abs/2611.12856) 的 145 个任务要求 Agent 自己决定是否拆分、谁处理哪些子任务、如何集成交付，使用隐藏 verifier 检查最终 artifact。研究显示没有一个固定的协作拓扑在全部领域最优，组织方式本身是可以评测的能力。

[Skill Adapter](https://arxiv.org/abs/2611.17007) 则尝试在不重写通用 Skill 的前提下，从真实执行反馈中沉淀个性化修改，并让路由器动态挑选适用 Skill。相比单一检索“最像的 SOP”，更接近 **通用 Skill + 当前上下文 Adapter + 执行反馈** 的组合。应警惕长期积累的 Skill/Adapter 冲突和负迁移。

### 6. Agent-native 训练数据要和可执行 Verifier 共同设计

[daVinci-Prover](https://arxiv.org/abs/2611.16433) 在证明任务中引入分解、搜索、自我验证和修订等 Agent 原生的中训练材料，并利用 Lean verifier-gounded 轨迹做 SFT。相较匹配的 Qwen3-8B SFT-only 基线，三个证明集平均提升 13.7pt。形式证明的可验证性强于开放式搜索，因此不能直接外推幅度，但“先设计可验证交互环境，再合成训练轨迹”的思路可直接借鉴。

[NIBench](https://arxiv.org/abs/2611.15831) 的另一侧面也值得注意：蒸馏出的 Skills 并非总能在未见任务上稳定提升，必须同时报告 seen/unseen、跨模型迁移以及可复现证据质量。

### 7. MCP 的实际新增是文件扩展实验与发布节奏，不是新稳定版

[11 月 10 日官方文件扩展探索](https://blog.modelcontextprotocol.io/posts/exploring-file-uploads-and-downloads-in-mcp/) 提出 `io.modelcontextprotocol/files` 和 `x-mcp-file`，大文件直接经授权目标传输，避免把 PDF/CSV/ZIP 的字节流塞进模型上下文。**目前属于实验提案、无稳定参考实现**。

[11 月 11 日官方公告](https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/) 宣布计划改为半年发布周期，下一目标是 2027-03-30。**截至本次检索，已正式发布的规范仍为 2026-07-28**，本周没有新正式 MCP 规范版本。对 MCP Gateway / ToolHub，先验证当前版本兼容性与权限控制，不应把 proposal 当作上线要求。
